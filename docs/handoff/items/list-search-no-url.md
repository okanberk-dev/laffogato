- This PR has no plan section: this note is its spec (privacy finding from the shell-nav review, #142).
- The panel list pages' own search boxes (siparisler, musteriler, urunler, menu, karaoke, bulten and any FilterBar with a free-text `q`) submit with GET, so a typed e-mail or phone lands in the URL: address bar, history, proxies and the Vercel request logs (PII).
- Fix centrally in the kit FilterBar: the free-text box never goes into the URL. Recommended: the FilterBar search posts to a small server action (session + section checked, rule 27) that stores the text in a short-lived, httpOnly, sameSite=lax, path-scoped cookie per list (e.g. `adm_q_<list>`, 10 minutes) and redirects to the same list URL without `q`; the list page reads the term from that cookie (and still accepts a non-PII `q` from old links but strips it from the visible URL with a redirect). Non-PII filters (status tabs, dates, sort, page) stay in the URL. Keep "Sıfırla" clearing the cookie. Saved views (UI-11) must not store the term either.
- If a cookie is the wrong tool for some list, decide and document; the requirement is: no PII-like search term in any URL the panel produces (use the pii-like helper from ui-search-route if merged).
- Tests: FilterBar markup has no GET text field named q; the action sets the cookie and redirects without q; each list reads the term; a static test lists every FilterBar usage.
